# Lens 08 — Ownership of a complete job

Input manifest SHA256: `748f176be9d48ccf383ff6a6a601b56e7a8337bc898d27c2f1c319462a7e9852`. Assignment: COD-87. First draft; no other lens reports read.

**Verdict: revise overall; narrow local ownership; paid value remains unresolved.** Codeweb can plausibly take over a bounded factual collection job: assemble source-linked context and mapped relationships for a declared task and revision. It does not take over the architecture/reuse decision, complete runtime impact assessment, or behavioral validation. The paid proposal is coherent only if it owns agreed check coordination through delivery and recovery, beyond adequate ordinary CI. Neither end-to-end customer outcome is demonstrated by the packet.

The strongest surviving formulation is: **collect and keep inspectable task evidence current within a declared source boundary; for the paid hypothesis, operate agreed checks and deliver their current outcomes with owned exceptions.** A complete bounded factual job need not make human decisions. It does have to finish its own refresh, provenance and delivery steps. This is a proposed refinement, not a charter amendment or build authorization.

## Findings

### L08-F01 — narrow

Narrow local ownership to assembling inspectable source evidence for a declared task; the product does not own the reuse or change-scope decision.

**Actor/task and conditions:** Agent-heavy developer extending shared utilities or inspecting cross-file consumers; CW-T018 supports the task but does not establish a representative customer segment. Supported source language/layout, available source, resolved target, explicit coverage; utility semantics and architectural boundaries remain human judgments.

**Strongest case:** The utility-duplication report exposes repeated orientation work. Context packs provide target bodies and caller windows; ranked similarity candidates can reduce the factual search portion. Supporting records: CW-T018.

**Strongest countercase:** Native search can already suffice in clean code. Generated members may evade source navigation. Neither mapped relations nor token-shingle similarity establishes complete runtime scope or substitutability. Counterevidence: CW-X001, CW-Z011.

**Failure scenario:** A developer receives two similar helpers, rereads both and every original caller, and still designs the abstraction unaided; a short list changed the presentation but removed no work.

**Weakest assumption:** Assembling this evidence removes searches the developer would otherwise repeat, rather than adding candidate verification.

**Local implication:** Define completion as a revision-bound, source-linked evidence packet with omissions and one inspectable next step. Measure changed inspection/reuse behavior separately; never market architecture ownership.

**Paid implication:** This single-repo collection belongs in free local capability; its savings cannot justify a paid coordination fee.

**Smallest falsification test:** On one consented shared-utility task and one matched native-search task, record initial plan, every lookup, candidate rejection and final inspection. Reject complete-job wording if users must rebuild the evidence packet; retain only an inspection aid if it changes no decision.

**Evidence type and confidence:** inference from first-person report and inspected repository capability. High confidence in inspected mechanism boundaries; low confidence in net task savings because no Codeweb participant outcome is present.

**Capability/proposal pointers:** CAP-context, CAP-similarity, PROPOSAL-strategy.

### L08-F02 — revise

Freshness and uncertainty handling are part of the collection job; reporting that a map is stale does not itself take over refresh and recovery.

**Actor/task and conditions:** Developer switching branches or revisiting a shared implementation across sessions, including large or partially mapped repositories. Distinguish the ordinary graph advisory from explicit evidence capture/reconciliation. The latter has task/root/profile checks and hash-based evidence, but selected files do not prove host activation or automatic recovery.

**Strongest case:** An adjacent reference-query failure returned empty results after a server crash. Codeweb explicit receipts preserve source-bound relationships and unresolved questions, a useful basis for avoiding silent disappearance. Supporting records: CW-Z007.

**Strongest countercase:** Existing receipt reconciliation already does more than return an unversioned list. Conversely, known-context work can need no extra retrieval; configuration and verification work can erase tool savings. Counterevidence: CW-Z012.

**Failure scenario:** The user sees stale evidence, manually refreshes, chooses a baseline, diagnoses a missing caller and then repeats the original search. New maintenance consumes the saved collection time.

**Weakest assumption:** Readiness, refresh, baseline choice and recovery can be made routine without hiding unsupported or uncertain evidence.

**Local implication:** Count installation, permission repair, cold mapping, baseline selection, stale recovery, interpreting omitted counts and retiring old exceptions in the local job budget. Saved exceptions are proposed, not demonstrated here.

**Paid implication:** A hosted service must own reruns and stale-result invalidation operationally; merely sending stale-status notifications relocates maintenance to repository owners.

**Smallest falsification test:** Before participant testing, use a supported host and a recorded task, change revision mid-flow, remove source access, and reopen the session. Observe who refreshes and reconstructs context. Fail ownership if the user silently acts on old evidence or must manually assemble the same facts again. This is a proposed preflight, not executed.

**Evidence type and confidence:** repository observation plus inference from adjacent-tool accounts. High confidence in the inspected receipt/advisory distinction; host behavior and net recovery burden remain unmeasured. Serena fix history is version-specific and not a current blanket defect.

**Capability/proposal pointers:** CAP-freshness, CAP-receipt, CAP-core, PROPOSAL-strategy.

### L08-F03 — narrow

A factual structural collection job can be complete while behavioral validation remains explicitly unfinished; tests require a separate execution and interpretation owner.

**Actor/task and conditions:** Developer and reviewer checking an agent-produced change before merge. Preserved source revisions, real test commands/results and explicit skipped/failed/unknown statuses; a valid test oracle and relevant environment are required.

**Strongest case:** Reports of premature completion and green tests that repair the application show why a structural result cannot close the validation job. The charter forbids executing analyzed code in the local analysis path. Supporting records: CW-X013, CW-T022, CW-Z004.

**Strongest countercase:** Ordinary type checking and CI can own repeatable checks; the strategy already requires real project test provenance rather than claiming static proof. This narrows the promise without making source collection useless. Counterevidence: CW-Y007.

**Failure scenario:** A reviewer sees unchanged relationships and a green status copied from a previous revision, assumes the feature works, and misses runtime breakage or an invalid test oracle.

**Weakest assumption:** Users correctly distinguish structural equality, successful command execution and validated behavior when presented together.

**Local implication:** Codeweb can own structural evidence capture; project tooling/agents execute tests and maintainers judge oracle adequacy and product intent. Do not count these retained responsibilities as tasks taken over.

**Paid implication:** The proposed service may coordinate explicitly permitted test runners and capture outcomes; it still does not choose business correctness or certify arbitrary compatibility.

**Smallest falsification test:** Give a reviewer a deliberately stale test result, a skipped check and an unchanged structural receipt for a changed implementation. Ask what is established and what remains. Fail the completion claim if any unavailable behavior check is treated as passed. No trial executed here.

**Evidence type and confidence:** inference from public self-reports, charter and inspected source. High confidence in logical and charter boundary; public incidents are unverified and not prevalence evidence.

**Capability/proposal pointers:** CAP-core, CAP-receipt, BOUNDARY-charter, PROPOSAL-strategy.

### L08-F04 — revise

The plausible paid complete job is revision-aware coordination of agreed checks through result delivery and failure recovery; demand and superiority over CI remain unresolved.

**Actor/task and conditions:** Developer champion and repository owners coordinating backend/frontend checks; buyer authority is not demonstrated. Explicit repository relationships, access policy, supported commands, named check owners, tested revision tuple, rerun triggers and a destination already used by reviewers.

**Strongest case:** The original account describes recurring manual invocation. A bounded service could own dispatch, tracking, rerunning, failed-run recovery and packaging outcomes for each agreed producer/consumer revision. Supporting records: CW-Y007.

**Strongest countercase:** The same author accepts CI as more appropriate. Isolation evaluation and service reliability can introduce new work. No measured Codeweb service, buyer, payment or renewal establishes additional value. Counterevidence: CW-Y004, CW-Y002.

**Failure scenario:** Every producer change still requires an owner to discover consumers, ask for access, choose revisions, chase runs and paste results into the PR; the paid service only adds a dashboard.

**Weakest assumption:** Enough recurring coordination remains after an adequate two-repo CI setup to pay for service operation and maintenance.

**Local implication:** Free local results remain inputs, not paywalled proof; local convenience must not be attributed to hosted savings.

**Paid implication:** Offer only an agreed check-coordination boundary: take responsibility from eligible revision event to current delivered result or explicit owned exception. Humans retain relationship policy, compatibility requirements and merge decisions.

**Smallest falsification test:** With one consenting team and an already identified recurring check, compare two change cycles against adequate CI plus ordinary PR links. Record dispatch/chasing/rerun/sharing minutes, setup and policy upkeep separately. Reject this paid job if the CI control completes it equally well or if users still do the coordination. Purchase/renewal requires later real evidence.

**Evidence type and confidence:** inference from first-person cross-repo report and unbuilt proposal. Medium confidence that the reported manual invocation exists; low confidence in recurrence scale, buyer fit and paid-attributable net savings. This is a proposed service, not an implemented runner.

**Capability/proposal pointers:** PROPOSAL-strategy, BOUNDARY-charter.

### L08-F05 — revise

Handoff is complete only when the recipient can use current evidence without reconstructing it; producing a receipt or summary alone is not result sharing ownership.

**Actor/task and conditions:** Change author handing work to a reviewer or another repository owner. Recipient access to source/revision and check provenance, clear unresolved items and named next owner; ordinary PR history is the baseline.

**Strongest case:** The review-workload account found summaries insufficient. Immutable source-linked records can reduce repeated reconstruction only if the recipient actually receives and understands them. Supporting records: CW-Y012, CW-Z004.

**Strongest countercase:** Paid review can provide value even on infrequent complex changes, but that is not evidence for Codeweb receipts. Existing specs, CI artifacts and PR history may already complete the handoff; an extra summary may add reading. Counterevidence: CW-Y001, CW-Z012.

**Failure scenario:** The author saves a local receipt, the reviewer cannot resolve its local workspace path or tested revision, and both spend another conversation reconstructing context. A complete producer artifact leaves the recipient job incomplete.

**Weakest assumption:** A concise evidence handoff eliminates reconstruction without shifting it to reviewers or maintainers.

**Local implication:** Task/root-bound local receipts are useful evidence machinery; cross-person portability and consumption are not proven by reading their serialization code. Keep source-policy boundaries visible.

**Paid implication:** Paid sharing must deliver into the existing review destination with access, current revisions, pending-owner state and failure recovery. A separate destination is not independently valuable.

**Smallest falsification test:** Hand one real task packet to a reviewer unfamiliar with the author session, compare with an ordinary PR/CI packet, and record clarification requests plus correct identification of checked revisions and unresolved work. Fail handoff ownership if they must repeat collection or cannot identify the next owner.

**Evidence type and confidence:** inference from practitioner report and inspected receipt serialization. Medium confidence in the handoff mechanism; no direct Codeweb recipient-use experiment or paid outcome. Adjacent accounts are distinct contexts, not a pooled success rate.

**Capability/proposal pointers:** CAP-receipt, CAP-core, PROPOSAL-strategy.

## Net work and experiment boundary

Count total work across author, reviewer and repository owner: task search + source reading + setup amortization + refresh/recovery + candidate rejection + tests/triage + handoff reconstruction + shared-result upkeep. Waiting time and human/agent active work should be recorded separately. A six-line response and faster query are insufficient if downstream work rises. Do not deduct necessary human architecture judgment as if automation had removed it; compare the factual collection and coordination parts with the same native baseline.

The frozen proof sprint already proposes matched native controls, independent adjudication, total-effort measurement and later voluntary use. Add the ownership map as a task-level ledger: who actually completed each stage, what was repeated, and which failures returned to the user. Keep the ten-change pilot threshold provisional. One task can falsify a claimed complete workflow; it cannot establish recurrence, retention or willingness to pay. No proposed test was executed in this read-only assignment.
