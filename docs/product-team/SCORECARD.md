## Operational definitions

**Activation:** a consenting qualified participant completes a real source-backed useful inspection/reuse decision. Track setup completion and first valid invocation separately. Record request-to-useful-decision time and facilitator help; no universal target is invented from absent data.

**Task value:** adjudicated additional correct actionable findings, null findings, misses, unwanted edits/abstractions and unresolved cases. Separate consumer scope from reuse. Preserve the pilot's two-findings/ten-changes/no-higher-median-effort rule as provisional, not a PMF threshold.

**Total effort:** setup, graph/refresh, permission/recovery, source reading, author/reviewer work and normal verification. Report cases/pairs/distributions and one-time setup. Available model tokens and stdout bytes have separate fields; missing tokens/costs remain unknown.

**Opportunity-based return:** among enrolled people with an observed later eligible opportunity, report actual optional useful use divided by that eligible group, with numerator and denominator. Show no-opportunity, access failure, prompted use, automatic delivery and unknown separately. A five-person cohort has no statistical retention benchmark; familiarity can legitimately remove future need.

**Acquisition:** per chosen channel, record qualified conversations -> consent -> completed setup -> useful task -> later eligible use, with actual counts and the source/date. Voluntary self-reported discovery source is directional attribution. Stars, downloads and impressions may be context but are not activated users.

**Paid value:** actual recurring residual check coordination after adequate CI, minus setup/amortization stated explicitly, maintenance, recovery, triage, policy work, service fee and delivery costs. Distinguish perceived benefit from cash savings. Name check/policy/budget owners. Purchase and renewal are separate real decisions; a wage illustration is not measured ROI.

**Execution health:** time waiting on dependencies, correction cycles, stalled handoffs, active operator/agent coordination time and available compute usage. Record planned review/setup separately from rescue; do not invent costs from subscription coverage or claim fewer interventions without a comparator.

## Result record

For a technical or user result record: result ID/date, work ID, claim/finding/test IDs, candidate/source/host/model identity, case/job/condition, method, observation, counterexample/unknowns, correctness/action/harms, effort/cost availability, private evidence locator or publication-approved link, reviewer method, decision affected and next action. Label planning, technical verification, reported customer behavior and observed customer behavior separately.

Raw participant source/contact/recordings stay private unless explicitly authorized for publication. Use anonymized case IDs in versioned public records. Never publish credentials, private code or consent-sensitive transcripts merely because the project repository is public.

## Updating and checking off work

TASKS.json holds execution states: planned, ready, in_progress, conditional, awaiting_send_authorization, later, done or cancelled. A ready task's declared dependencies must be complete. Keep user-outcome status separate. A completed output can have unobserved/refuted/inconclusive benefit; a failed experiment can deliver complete learning.

At completion or handoff, attach the actual result, update task state, append the decision change to RESULTS.jsonl, reconcile CURRENT.md and the GTM roadmap, and regenerate the readable finding table when DECISIONS.json changes. Reopen the affected decision when counterevidence contradicts it. Do not rewrite original evidence or silently move a success criterion.

At a session restart, read CURRENT, the selected task and relevant spec/results; verify files/commit before resuming. Recommend one weekly active-work review of priorities, recent user evidence and stalled tasks. No recurring agent or scheduled job is installed by this plan.

## Refresh triggers

Review active findings when their source/package/host surface changes; the selected user's job or alternatives change; real trials contradict them; a candidate contact or consent changes; a paid decision depends on current costs or competitor capability; or the next action relies on an old factual baseline. Refresh the smallest affected source set and record last-reviewed date, version identity and reason. An old report remains historical evidence, not a verified current product capability.

The manual [planning validator](../../reports/research-to-execution-plan-2026-09-30/validate.py) checks finding/claim/test coverage, links, source hashes and task dependencies. It does not establish strategy quality, user outcomes or automated plan maintenance.
