# How Codeweb will be measured in the pilot

The local product has usage counters; it sends no product telemetry to the founder. `stats.json` stays beside each participant’s graph and `CODEWEB_NO_STATS=1` disables writes. Its counters and dates describe calls, maps, brief/card delivery and flagged structural regressions. They do not establish correct decisions, prevented bugs, customer identity or voluntary reliance. The sibling pending-card file contains symbols and relative filenames, so we will not ask for a raw `.codeweb` folder dump.

The existing weekly acquisition ledger records public npm retrievals and GitHub counters. Its September 28 successful run recorded 94 weekly downloads; this does not identify 94 users. External gate adoption was unknown (`null`), not zero. Weekly vitals checks source health, not behavior. Website source has no tracking implementation; its downloads page reads the public npm API.

For five consenting participants, measure actual tasks through private, explicit records: what they intended to inspect, their capable normal inspection, what Codeweb changed, source-backed correctness, all actual effort/help/recovery, harms, and later optional use when another eligible task exists. Optional local-counter sharing is participant-reviewed and limited to agreed aggregate fields. No automatic upload, new account, hosted analytics sink or local product instrumentation is added.

The list starts as discovery prospects from public episodes and opt-ins. A source signal is not a qualified participant. Current host/job/opportunity, appropriate route, previous contact, reply and consent must be recorded before enrollment. Contact details, messages, private code and raw study data stay outside the public repository.

Before observation, freeze the protocol, task/order allocation rule and independent adjudication method; obtain actual permission and confirm the required people/setup. Missing information remains missing. An empty tracker means no observations, not measured zero retention.
