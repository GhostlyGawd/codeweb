# Local Codeweb value pilot — prepared protocol

Experiment ID: LOCAL-01. Status: prepared; allocation must be frozen before enrollment/measurement. Owner: Codex. Work: E-01/E-02/E-03/D-01. Sources: F-C01/F-C04/F-C05/F-C12 and F-T01/F-T04/F-T05/F-T12. No participant trial or outreach has been performed by creating this protocol.

## Decision and separate hypotheses

Scope: Codeweb changes a maintainer's inspection decision by providing an additional correct relevant supported reference/consumer at acceptable total effort.

Reuse: Codeweb identifies a candidate implementation whose comparison correctly changes the plan, beyond competent native search and the developer's ordinary duplication tools. Reuse suitability remains the maintainer's decision.

Analyze these separately; counts of retrieved relationships, duplicate lines, delivered cards and calls are exposure/mechanism measures. A small field result is not a population effect or PMF proof.

## Entry and participants

Freeze a technically ready NED candidate, actual host/model versions, relevant source scope, the scoring rules and task allocation. Aim for five consenting ordinary maintainers and ten actual changes (two per person). Recent unresolved reference/reuse uncertainty is the screening criterion. Label tool-builder, reviewer and buyer roles, and report them separately rather than quietly replacing the primary cohort.

Seek both Claude Code and Codex users where qualified participants permit; record any host imbalance. Do not change somebody's host/provider to fill a quota. Existing user counts remain unknown. An invitation, positive reply or generated persona is not a participant/task outcome.

Raw source, transcripts and personal/contact data remain private by default. Obtain explicit consent for observation, any recording, follow-up, and any public/anonymized case publication. Store only agreed data; public GitHub carries sanitized aggregate results or cases with specific publication consent. No telemetry is added to the local product.

## Allocation to freeze

Proposed allocation is three scope pairs and two reuse pairs across the five participants, with condition order counterbalanced within each pair. Reassign by naturally available task type before measurement if this allocation is not feasible and record the reason. Two distinct comparable real changes per person; never have one person repeat the same change as an independent timing comparison.

Include naturally occurring familiar native-success work, same-file reference cases, intentional duplication and generated/runtime or nonstructural dependencies where available. These are negative/control conditions to retain, not planted tasks to guarantee a win. Record task type, uncertainty, prior familiarity and suitability before seeing Codeweb output. If real opportunities do not supply the intended coverage, report the shortfall and its limits.

The native condition keeps usual grep/LSP, source access, tests, instructions, clone detection, PR/CI and expert help. It has no active Codeweb tools/hooks/instructions. The treatment adds the frozen Codeweb workflow with the same host/model, source access and normal validation. Use separate clean configuration/session states and verify treatment exposure; an installed package alone does not establish exposure. Record contamination/learning between distinct tasks.

## Procedure and evidence

1. Record the real change, current workaround, relevant uncertainty and competent native inspection plan. In a treatment case, let the normal native inspection stage run before recording what the added evidence changes; an initial uninformed guess is not a capable baseline.
2. Freeze the source identity and a source/maintainer-grounded relationship or reuse oracle, including unknown dynamic/semantic coverage. The oracle is a validity check, not a fabricated exhaustive map.
3. Execute the assigned condition without coaching preferred decisions. Record actual tool/context delivery, inspections, candidate dismissals, edits, checks, failures and any assistance. Distinguish inability to access the workflow from rejection of the job.
4. Capture all setup, mapping, refresh, permission, recovery, reading, author/reviewer and usual verification effort. Record one-time setup separately and include it in observed treatment totals; do not amortize it over invented future task frequency. Report per-case time, pair differences and distributions, with available token usage separately from stdout bytes.
5. Require an adjudicator other than the decision maker for findings counted toward the provisional gate. Retain disagreement and unresolved judgments. Freeze the authorized adjudication method before the pilot; if an adjudicator is unavailable, the case remains awaiting adjudication and cannot support an unqualified pass. Do not manufacture independence.

An additional actionable finding is a correct source-backed relationship or candidate that changes an inspection/reuse decision beyond the recorded competent pre-brief stage and is confirmed relevant by task/source adjudication. Keep this bounded definition separate from a stronger claim that the native workflow would never have found it later. Matched native tasks and usual checks provide context; this small design does not prove a general causal effect.

## Provisional decision rule

Preserve at least **two additional correct actionable findings across ten changes** with **no higher median total combined inspection/review effort** in the Codeweb condition versus competent native controls. Show all ten cases and the five pairs, as well as scope/reuse subgroups and participant distributions. Equal-time correct additions count. Faster incorrect output fails. Pure equal-quality time savings are retained as a separate efficiency outcome and do not pass this actionable-findings gate.

Adjudicate severe misses, unwanted edits and inappropriate abstractions individually. An unresolved material harm prevents an unqualified pass even if the median is favorable. There is no invented acceptable harm rate. If participation/eligibility falls short, report an incomplete pilot rather than claiming the ten-case rule passed.

A pass supports another bounded learning decision. It establishes neither repeated reliance nor permission to expand into a hosted platform or market the replay's numbers as customer savings.

## Follow-up within the proposed two-week window

After initial work, permit optional later use and follow up only through the authorized/consented route. Classify actual optional use, prompted/automatic delivery, eligible nonuse, no eligible opportunity, inaccessible workflow and unknown separately. Ask for the actual task and changed decision, including cases where familiarity or exported learning removed the need to return.

Two tasks and this follow-up do not establish post-familiarity withdrawal loss. F-T06/F-T07/F-T08/F-T10 remain separate, larger follow-on studies. Do not manufacture an eligible task or silently extend observation/reminders.
